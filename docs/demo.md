# 데모 운영 노트

2026-09-19 실측 기준. 여기 적힌 숫자는 전부 RTX 3090 · Qwen3-4B-Instruct에서
직접 잰 값이고, 추정치는 그렇다고 표시해 두었습니다.

실수는 전부 **한 가지 모양**이었습니다: 화면이 멀쩡해 보이는데 측정이 틀린 것.
빠른 결과가 나오면 성공처럼 보이기 때문에, 아래 확인 항목을 먼저 보세요.

---

## 먼저 볼 것: 배지

전송 후 말풍선 아래 배지 하나가 모든 걸 말해줍니다.

| 배지 | 뜻 | 시간 |
|---|---|---|
| `입력 30,927 · bypassed` | 정책을 읽었고 캐시는 안 씀 — **최적화 전** | ~10.7s |
| `입력 30,927 · hit` | 정책 KV 재사용 — **최적화 후** | ~2.8s |
| `입력 75 · off` | **정책이 프롬프트에 없음** | ~2.8s |

세 번째가 함정입니다. 2.8초가 나오지만 **최적화된 게 아니라 읽은 문서가 없는
것**입니다. 입력이 네 자리가 아니면 그 실행은 비교에 쓸 수 없습니다.

---

## 실수 1 — "왜 항상 2초야?"

**증상:** 문장을 바꿔 가며 여러 번 눌러도 계속 2초대.

**원인:** 캐시가 이미 올라가 있어서. 정책은 고정 prefix이고 이벤트는 뒤에
붙으므로, 이벤트를 바꿔도 prefix는 그대로 재사용됩니다. 그게 이 최적화의
요점이기도 합니다.

**해결:** `추론 최적화 전으로`를 먼저 누르세요. 그게 캐시를 우회합니다.

---

## 실수 2 — 캐시를 비우면 느려질 거라는 착각

**하면 안 되는 것:** 데모를 초기화하려고 `캐시 해제`를 누르는 것.

캐시를 비우면 느려지는 게 아니라 **정책이 프롬프트에서 통째로 빠집니다.**
서버는 prefix가 없으면 짧은 대체 템플릿을 씁니다. 결과는 `입력 75 · off`,
2.6초, 그리고 엉뚱한 출력.

실제로 이렇게 나왔습니다:

```
첫 토큰 0.06s · 전체 2.62s
{"security_issues": [{"type": "exposed_api_key", ...
```

0.06초는 30,857 토큰 프롬프트에서 **물리적으로 불가능**합니다. 그 숫자가
보이면 문서를 안 읽은 겁니다.

**지금은 버튼이 알아서 정책을 올립니다.** 그래도 `캐시 해제`는 데모 중에 누를
이유가 없습니다.

---

## 실수 3 — 전후 사이에 문장을 바꾸기

같은 프롬프트여야 비교가 성립합니다. 입력칸은 하나이고 실행 버튼도 하나이니,
**상태 버튼만 누르고 문장은 그대로 두세요.**

---

## 실수 4 — 서빙 중인 파드에 학습 걸기

**증상:** 2분쯤 뒤 CUDA OOM.

```
Process 3910603 has 22.63 GiB in use   ← 상주 중인 추론 서버
23.56 GiB 중 남은 것 7.69 MiB
```

**지금은 막힙니다.** 배치가 작업 전에 GPU와 디스크 여유를 파드에 직접 물어보고,
자리가 있는 다른 파드로 옮깁니다. 자리가 아무 데도 없을 때만 회수하고, 그때도
옛 체크포인트를 먼저 지우고 돌고 있는 서버는 마지막입니다.

---

## 실수 5 — 체크포인트 없는 파드에 추론 에이전트

**증상:** 동기화와 환경 준비를 다 마친 뒤 이런 에러.

```
OSError: Repo id must be in the form 'repo_name' or 'namespace/repo_name':
  '/workspace/gpushare/ckpt/run'
```

파인튜닝 체크포인트는 **학습을 돌린 파드 디스크에만** 있습니다. 추론 최적화는
그 파일을 읽으므로 옮길 수 없습니다.

**지금은 이렇게 말하고 멈춥니다:**
`pod X has no trained checkpoint — the last run left one on Y; pick that pod`

---

## 실수 6 — 디스크 꽉 참

**증상:** 500스텝을 다 돌리고 마지막 저장에서 실패.

```
SafetensorError: No space left on device (os error 28)
```

컨테이너 디스크는 40GB이고 HF 캐시가 금방 9GB를 먹습니다. 배치가 이제 디스크도
확인하지만, 여러 모델을 올려본 파드는 수동 정리가 필요할 수 있습니다.

```
rm -rf /root/.cache/huggingface/hub    # 필요한 것은 다시 받습니다
```

## 진행 순서

Step 2 하나로 끝납니다.

```
1. [ 추론 최적화 전으로 ]
2. 문장 붙여넣고 [전송]
     → "첫 토큰 대기 8.6s — 정책 30,857 토큰을 처음부터 읽는 중"
     → 글자가 2초간 흐름
3. [ 추론 최적화 에이전트 ]
     → 워크로드 분석 표시
4. 같은 문장 그대로 [전송]
     → 즉시 시작
```

### 붙여넣을 문장

```
A contractor emailed an API key to a personal address.
An intern shared a service account token in a group chat.
A team lead reused the same admin password across three internal systems.
```

마지막 것만 `RISK: Unauthorized access via reused credentials`로 다르게
답합니다. 나머지 둘은 `Credential exposure`입니다.

**쓰지 마세요:** `An employee uploaded a customer list to a personal cloud
drive.` — 고객 명단 유출인데 `Credential exposure event`라고 답합니다. 정책이
온통 credential 얘기라 모델이 그쪽으로 끌려갑니다.

## 실측값

```
                 첫 토큰    전체    출력     입력
최적화 전         8.70s   10.80s   49 tok   30,927 · bypassed
최적화 후         0.64s    2.88s   51 tok   30,927 · hit
                  13.6x     3.7x
```

문장을 바꿔도 전체 시간은 10.65~10.80s로 같습니다. 입력의 99.8%가 정책이고
이벤트는 2토큰쯤 차이나기 때문입니다.

### 말할 때 정확한 문장

> 반복되는 정책 prefix의 **prefill**을 캐싱해 10.8초에서 2.9초로 줄였습니다.
> 첫 토큰까지는 8.7초에서 0.6초입니다.

**"모델이 4배 빨라졌다"는 틀립니다.** 생성 자체는 그대로입니다 — 양쪽 다 같은
49~51 토큰을 만들고, 그 시간은 2초대로 동일합니다. 없앤 것은 30,857 토큰을 다시
읽는 일뿐입니다.

### byte 동일성은 주장하지 마세요

각 경로는 결정적입니다(greedy 3회 반복이 정확히 같음). 하지만 두 경로가 서로
byte 동일하지는 **않습니다.** 캐시 없는 쪽은 30,892 토큰을 한 번에 prefill하고,
캐시 쪽은 30,857을 미리 채운 뒤 35개를 붙입니다. 텐서 모양이 다르면 커널과
리덕션 순서가 달라지고 bf16에서 거의 동률인 토큰이 갈립니다.

실제로 관찰된 차이: 문자 14에서 `"risk": "high"` vs `"risk": "High"`.

화면이 이 불일치를 숨기지 않고 갈린 지점을 보여줍니다.
