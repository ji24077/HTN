Implementation architecture

Work scheduled across computers you trust

A review of the two-workload MVP: what the topology can actually deliver, where the handoff overclaims, and the gates that decide whether the product thesis survives contact with two real machines on two real networks.

Executive answer

A two-computer cross-network demo is achievable under the stated constraints. Nothing in Checkpoint A requires a capability that does not exist. Host-initiated outbound WSS on 443 to a public control service is the same mechanism behind every mainstream remote-access and CI-runner product: no inbound ports, no VPN, no UPnP.

Three things in the handoff are overclaimed or underspecified, and are corrected below.

  1. The 1.2× stretch speedup has a hard floor on batch size. With the illustrative host rates in §7, the batch needs ≥ ~680 items before 1.2× is arithmetically reachable, regardless of scheduling quality. Smaller batches cannot pass.
  2. "Proof of distribution" is not provable from the control service's own logs. The service writes those logs; a faked demo produces identical ones. Host-signed result attestations are added so provenance is verifiable by a reviewer who does not trust the server.
  3. Storing observed_egress_ip on the Host record is both unstable — CGNAT, tethering, VPN toggles — and a standing privacy cost. It becomes an on-demand probe, recorded per browser session only.

No end-to-end confidentiality claim

The two bolded rows are the trust-model core and must appear in the product UI, not only in this document. Relayed frames transit the control service in plaintext-over-TLS and are decryptable there. The MVP makes no E2E claim, and marketing must not imply one.

2Pairing, authentication, revocation, NAT

Enrollment

  1. Signed-in user clicks Enroll computer → POST /hosts/pair-code → a code such as K7M2-P4QX. Eight characters, Crockford base32, single use, 10-minute TTL, bound to a user.
  2. On the target machine: dwp-agent pair --server https://control.example --code K7M2-P4QX.
  3. The agent generates an Ed25519 keypair locally and writes the private key to ~/.dwp/agent.key at mode 0600. It refuses to start if permissions are wider. A Keychain and DPAPI storage deferred to hardening.
  4. POST /hosts/pair validates the code and marks it consumed in the same transaction that creates the host row.
  5. The code is never reusable, never logged, and grants nothing by itself — it authorizes the binding of one public key.

Why asymmetric rather than a bearer token: the control database then holds no credential that can impersonate a host. A database read compromise cannot forge host results, which is exactly what makes the attestation in §12 meaningful.

Session authentication

The agent connects to wss://control.example/agent/connect presenting an EdDSA-signed JWT: {iss: hostId, aud: "dwp-control", iat, exp: iat+120, jti}. The server verifies against the stored public key, rejects clock skew beyond 120 s, and rejects a replayed jti from a ten-minute cache. Reconnects mint a fresh assertion. No long-lived bearer token exists on the wire.

Pause and revoke are different things

ActionWhoEffectReversible
PauseHost owner, locally or via dashboardNo new placements; running tasks finish; browser sessions endYes, instantly
RevokeHost owner or adminrevoked_at set; socket closed with code 4003; agent stops retrying and self-disablesNo — re-pair required

The local pause switch must work with the control service unreachable. It is a local file flag the agent reads, not a server round-trip.

NAT and transport

Outbound TCP/443 with TLS and a WebSocket upgrade traverses ordinary home NAT without configuration, because the connection is established from inside. No inbound listener exists on the host. Keepalive is a WS ping every 15 s; the server marks a host offline after 45 s without a pong; the agent reconnects with full-jitter exponential backoff capped at 60 s.

The one environment this fails in is a network with a TLS-inspecting middlebox or a proxy that blocks WS upgrades. A To be confirmed on both real networks in Pass 1. The fallback — long-poll plus POST — is strictly worse and should be built only if measurement proves it necessary.

No exposed CDP

  • Chromium is launched through Playwright's chromium.launch(), which drives the browser over a stdio pipe rather than a TCP debugging port. D Re-verified in Pass 3 by asserting no process carries --remote-debugging-port and no port is listening.
  • launchServer() and any --remote-debugging-port flag are forbidden; a lint rule and a startup assertion enforce it.
  • Chrome documents that an exposed remote-debugging port permits cookie extraction from the profile. D
  • The dashboard receives frames and sends semantic input events. It never receives a CDP endpoint, session ID, or WebSocket URL that reaches the browser directly.

Deviation from the handoff

observed_egress_ip is not on hosts. A host's egress address changes with tethering, VPN toggles, and CGNAT reassignment, so a stored value is stale and misleading precisely where honesty matters most. It is probed on demand for the fleet card — displayed, not persisted — and recorded on browser_sessions, where it is evidence about one specific run.

Task lifecycle

stateDiagram-v2
  [*] --> pending
  pending --> offered: offer
  offered --> leased: accept
  offered --> pending: decline
  leased --> running: start
  leased --> pending: lease expiry
  running --> pending: lease expiry
  running --> succeeded: result accepted
  pending --> failed: attempts = 3
  pending --> cancelled: cancel
  running --> cancelled: cancel
  succeeded --> [*]
  failed --> [*]
  cancelled --> [*]
  • Lease: granted for 30 s, renewed by the agent every 10 s. A sweeper every 5 s returns expired leases to pending and increments attempts.
  • Claim: SELECT … WHERE state='pending' ORDER BY seq FOR UPDATE SKIP LOCKED LIMIT $n inside one transaction that also writes the lease. Two schedulers cannot hand the same task to two hosts.
  • Idempotency: the terminal write is UPDATE tasks SET state='succeeded' … WHERE id=$1 AND state <> 'succeeded'. A late result from a superseded attempt matches zero rows and is logged as duplicate_result rather than an error. Every attempt survives in task_attempts, so the run map can show "ran twice, first accepted".
  • Cancellation stops new leases and signals holders. Already-succeeded results are kept and the job ends cancelled_partial with an explicit accepted-item count. Partial results are surfaced, never silently discarded.
  • Max attempts is 3. A task that fails on two different hosts is flagged as an input problem, not a host problem.

6Adapter interface and the two adapters

Each adapter is two halves — a planner on the control service and an executor in the agent — sharing a type from protocol/, which is what keeps them honest.

packages/protocol/adapter.ts
// agent side
interface WorkloadExecutor<I, O> {
  readonly type: string
  readonly version: string
  probe(): Promise<CapabilityRecord>                       // at connect + on change
  calibrate?(spec: CalibSpec): Promise<ThroughputSample>   // { itemsPerSec, setupMs }
  execute(input: I, ctx: ExecCtx): Promise<O>
}

interface ExecCtx {
  signal: AbortSignal                  // cancel, lease loss, or pause
  onProgress(done: number, total: number): void
  artifacts: { fetch(sha256: string): Promise<string> }   // verifies hash before returning path
  tmpdir: string                       // removed on completion
  limits: { cpuQuotaPct: number; memLimitMb: number; wallClockMs: number }
}

// control side
interface WorkloadPlanner<S, I> {
  readonly type: string
  validate(spec: S): Result<ValidatedSpec>
  eligible(host: HostRecord, spec: ValidatedSpec): Eligibility   // { ok } | { ok: false, reason }
  partition(spec: ValidatedSpec): I[]
}

Eligibility returns a reason on rejection, and the reasons are shown in the New work screen before launch. A scheduler that silently excludes a host is indistinguishable from a broken one.

cpu_inference_batch

  • Spec: { modelHash, preprocessingId, inputManifestHash, batchSize, perItemTimeoutMs, tolerance }
  • Eligibility: allow_compute ∧ ¬paused ∧ online ∧ os/arch supported ∧ free_ram ≥ footprint × 1.5 ∧ concurrency < max ∧ user under quota
  • Execution: fetch model and inputs by hash, verify SHA-256 before use — a mismatch is a hard failure, never a warning — create an ORT session with intraOpNumThreads bounded by cpu_quota_pct, run assigned items.
  • Correctness: floating-point CPU kernels are not bit-identical across microarchitectures, so the gate is max |Δlogit| ≤ tol with tol published — not equality. A Measured in Pass 2, not guessed.
  • Hard rule: one model request is never split across machines. Parallelism is across independent items only.

remote_browser_session

  • Eligibility: allow_browser ∧ trust_tier = 'trusted' ∧ ¬paused ∧ online ∧ no active session ∧ startUrl ∈ allowlist ∧ requester may use this host
  • Execution: launch the agent-local enforcing proxy (§9), then Chromium with --proxy-server=127.0.0.1:<port> and a fresh userDataDir under tmpdir.
  • Lifecycle: pinned to one host. Disconnect ends the session, closes the context, and deletes the profile directory. No cookie or live-state migration between machines — that boundary is what keeps the trust model coherent.
  • Output: frames (never persisted), an append-only session event log, and the observed egress address.

7Scheduling

Minimize makespan — the finish time of the slowest host — not average utilization and not cost. For host h given nh items:

T_h = q_h + s_h·(1 − cached_h) + n_h / r_h q_h estimated drain time of work already queued on h s_h setup + transfer: model_bytes / measured_bandwidth + warmup_ms r_h measured items/sec from the calibrations table cached_h 1 if the host already holds this model_hash

Water-filling with a tail pool

Binary-search the makespan T such that Σ max(0, r_h·(T − q_h − s_h)) = N. A host whose share computes to ≤ 0 is excluded — meaning its setup cost exceeds any contribution it could make, a real and common outcome for a cold slow host on a small batch. The UI says so rather than hiding it.

Ten percent of items are held back as a tail pool, dispatched on request as hosts finish. This is the handoff's "conservative reserve" made concrete: it absorbs calibration error and turns a host dropping offline near the end into a small tail rather than a stranded block.

Calibration is itself overhead. Results are cached per (host, adapter, model_hash, agent_version) with a 24-hour TTL, and a calibration batch is capped at min(64 items, 2 s). Recalibrating on every job would destroy exactly the small-batch case that is already marginal.

Worked two-host example

Illustrative rates, to be replaced by measured ones. N = 1000. Host A: r = 42 items/s, model cached so s = 0. Host B: r = 17 items/s, cold so s = 6.8 s.

42·T + 17·(T − 6.8) = 1000 59·T = 1115.6 → T = 18.9 s n_A = 42 × 18.9 = 794 items n_B = 17 × (18.9 − 6.8) = 206 items single-host baseline on A = 1000 / 42 = 23.8 s speedup = 23.8 / 18.9 = 1.26×

The batch-size floor — the most important number here

Generalizing with q = 0 and sA = 0:

T = (N + r_B·s_B) / (r_A + r_B) S = (N/r_A) / T = N·(r_A + r_B) / (r_A·(N + r_B·s_B)) S rises with N toward the ceiling (r_A + r_B)/r_A = 1.405 solving S ≥ 1.2 for these rates:
N ≥ 677 items

The 1.2× stretch target is unreachable on any batch smaller than ~680 items with this host pair, no matter how good the scheduler is. The demo dataset must be sized from measured rA, rB, sB before the benchmark runs, not chosen for convenience and explained afterwards.

And if the measured ceiling (r_A + r_B)/r_A is itself below 1.2 — which happens whenever one host is more than 5× slower than the other — the target is unreachable at any batch size. The correct response is to report that, not to hunt for a flattering configuration.

9Threat model

Malicious or curious host owner

Can read the remote browser's memory, profile directory, and network traffic; can install a root CA and inspect TLS; can tamper with results. Mitigations are the trust tier, browser sessions restricted to trusted hosts, test accounts and team-owned sites only, and prominent "Running on Host B — its owner can see this session" labeling. Result tampering is detectable only for verifiable workloads: agreement across hosts on overlapping items, which the tail pool supplies for free. Residual risk: accepted and documented. A host owner is inside their own machine; no MVP control changes that.

Malicious job submitter

Wants the host as an open proxy, a LAN scanner, or a code-execution surface. Mitigations: no arbitrary code or shell — only the two adapters; URL allowlist; private-range blocking below; per-user quotas on items, concurrent jobs, and session minutes; wall-clock caps per task.

Platform operator

Sees relayed frames, input keystrokes, job inputs and results, and all metadata. Frames are relayed, never written to disk; run_events excludes page content by default; log retention is bounded. End-to-end media encryption would require the control service to relay opaque bytes it cannot decode — a genuine possibility with WebRTC insertable streams later, and explicitly not a Pass 1–5 property.

Target sites

See automated traffic from the host's egress. Allowlist of team-operated domains only; robots and ToS respected; no marketing of geo-restriction bypass.

Accidental LAN and metadata access — the sharpest edge

A URL allowlist alone is not sufficient

DNS rebinding lets an allowlisted hostname resolve to 192.168.1.1 on the second lookup, and redirects can walk out of the allowlist. Enforcement therefore sits at an agent-local HTTP/HTTPS proxy bound to loopback, which the remote Chromium is launched against.

  1. Host must match the allowlist — exact host or an explicit suffix rule.
  2. Resolve the name once; reject unless every returned address is public.
  3. Pin the connection to the checked IP. The browser never re-resolves for itself.
  4. Deny 127.0.0.0/8, 10/8, 172.16/12, 192.168/16, 169.254/16 (including 169.254.169.254), 100.64/10, ::1, fc00::/7, fe80::/10, and any non-global IPv6.
  5. Re-run steps 1–4 on every redirect hop, with a hop cap.
  6. Deny non-HTTP(S) schemes, and file: / chrome: navigation via policy flags.

The proxy is small and fully unit-testable, and its test suite is a Pass 3 release gate. This is the one place where a quiet bug turns a friend's laptop into an attack surface against their own network.

10Stream transport and the upgrade trigger

Pass 3 uses a CDP screencast over the authenticated relay: Page.startScreencast({format:'jpeg', quality:60, maxWidth:1280, maxHeight:800, everyNthFrame:2}), frames forwarded as binary WS messages and rendered to a canvas. Input travels back as semantic events through the Playwright CDP session.

Backpressure rule — non-negotiable

At most one frame in flight per session. If a frame is pending when the next arrives, the older is dropped, never queued. Unbounded frame queues are the standard way this architecture dies: latency grows without bound while throughput still looks fine.

Expected cost A: roughly 30–120 KB per frame at 1280×800 / q60; at ~10 fps, 0.3–1.2 MB/s per session. Latency is RTT(web↔control) + RTT(control↔agent) + encode + queue. The UI displays the measured refresh rate and never implies 60 fps.

Move to WebRTC only if, over a 2-minute scripted interaction on the real pair

SignalThreshold
Input-to-visible-frame, p50> 250 ms
Input-to-visible-frame, p95> 600 ms
Sustained host uplink per session> 1.5 MB/s
Dropped-frame rate> 20 %

What that upgrade actually costs. WebRTC is not a drop-in. The agent becomes a media sender: the screencast is a stream of JPEGs, so it needs a real VP8/H.264 encode pipeline and a WebRTC stack in Node, plus ICE, plus a TURN server for symmetric-NAT pairs — which relays the media anyway and returns the operator to the plaintext position. That is why it is conditional on measurement rather than planned.

11Test protocol and phase gates

Every run records OS, CPU model, logical cores, RAM, network type and measured bandwidth, agent version, model hash, manifest hash, item count, cache state, timestamp, and the git SHA of all three packages. At least three warm trials per configuration; report median and full range, never a single best run. Baseline is the faster single eligible host on identical inputs, model, and preprocessing. The harness writes one JSONL record per trial and the run-history screen renders exactly those records — the UI cannot show a number the harness did not produce.

12Top five failure modes

1 · Duplicate or lost results around lease expiry

A host finishes as its lease expires; the task is already re-queued; two results arrive. Remedy: conditional terminal UPDATE, all attempts retained, late results recorded as duplicate_result. Test: SIGKILL an agent at 60 % of a batch and assert accepted == total with attempts > total.

2 · Distributed is slower than one host

Setup and transfer dominate. Remedy: the §7 floor is computed and shown before launch — "with your current hosts, this batch needs ≥ 680 items to beat Host A." The run map always shows the overhead breakdown. A result below 1× is a finding, not a bug to hide.

3 · Media backpressure collapse

Frames queue, latency climbs, the session becomes unusable while metrics look healthy. Remedy: one-frame-in-flight cap, drop-oldest, adaptive quality, hard session TTL, and latency measured end-to-end rather than at the encoder.

4 · SSRF or LAN reach from the remote browser

A redirect or DNS rebind points the browser at the owner's router or a metadata endpoint. Remedy: the §9 enforcing proxy with IP pinning and per-hop revalidation; its unit tests are a release gate.

5 · Fake distribution — the demo-integrity failure

The most damaging outcome

A demo that looks distributed but isn't, where the control service's own logs cannot disprove it — because the control service writes them.

Remedy: each result carries sign(host_privkey, {taskId, attempt, outputHash, startedAt, finishedAt, hostId}), stored in task_attempts.host_signature. scripts/verify-run.ts takes a job ID and the enrolled public keys and verifies every accepted result independently of the server's narrative. The run map shows a per-task verification badge. A reviewer who does not trust the operator can still check that two distinct machines did the work.

14Go / no-go and unresolved decisions

Recommendation · Go for Pass 1

The topology is sound, the stack is available on all three target operating systems, and the risky parts are isolated behind measurement gates rather than assumed away.

Two decisions gate Pass 1 and cannot be assumed

  1. Where does the control service run publicly? It needs a real TLS certificate and a stable hostname reachable from both home networks. A small managed host is the straightforward answer; a tunnel is acceptable for the spike but must not become the architecture.
  2. Which two physical machines, on which two networks? The handoff is explicit that a VM cannot substitute for the cross-network proof. If only one network is available today, Pass 1 stalls at the network gate regardless of code quality.
